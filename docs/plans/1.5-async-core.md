# 1.5: Async core on a Tokio runtime

Status: done

The design below is the approved plan, with factual errors the adversarial review found corrected
in place. The Review log at the end lists each finding and what changed.

## Goal

The core owns a Tokio runtime and its UniFFI API is `async`, so Swift awaits Rust calls instead of
parking a thread on them, and later steps can run network I/O (Google token refresh in 1.4, IMAP in
1.6) without blocking anything. Blocking work (SQLite, the Keychain callback) never runs on a Tokio
worker.

## Feature link

Foundation. Architecture, Threading: "Network work runs on a Tokio runtime owned by
`clientmail-ffi`". Moved ahead of 1.4 so Google sign-in is async from the start.

Notes from `docs/plans/README.md` this step must address:

- 1.5: "Call the synchronous secret store through `spawn_blocking` (or make the callback interface
  async) so a blocked Keychain call never stalls a Tokio worker." Resolved by the blocking pool
  rule below, with the callback kept synchronous.

## Scope

- Decision record 0008: who drives Rust futures, and why the Keychain callback stays synchronous.
- FFI: a `CoreRuntime` owned by `CoreClient`; every `CoreClient` method except the constructors
  becomes `async` and runs its work on the runtime's blocking pool.
- Swift: `CoreAdapter` awaits the generated async methods; `@concurrent` goes away.
- Docs: architecture (Data flow, Threading), `core/AGENTS.md` and `apps/macos/AGENTS.md`
  concurrency rules.

## Out of scope

- Async constructors. `CoreClient::open` stays synchronous and `Startup` still opens the database at
  launch on the main thread, as today; the window shell (1.10) can move it behind a loading state.
- Async engine use cases and async ports. Nothing in the engine does network I/O yet. How an async
  use case reaches the synchronous store and secret store is decided where it first happens (1.4
  token refresh, 1.8 sync); a note is added for both.
- Cancellation. UniFFI 0.32's Swift bindings do not support it: a cancelled Swift task keeps
  waiting until the Rust call finishes, and the work is never stopped. Fine for short calls; 1.4
  (sign-in closed mid-exchange) and 1.8 (long sync) need a core-level cancel, noted for both.
- Change events from the core to Swift (1.9).
- A connection pool for the store (1.8, already noted).

## Design

### Who drives the futures

UniFFI turns an `async fn` into a Swift `async` function. The Swift side polls the Rust future
through callbacks; the question is where the Rust work actually runs.

| | A. Own runtime, spawn onto it (recommended) | B. UniFFI's `async_runtime = "tokio"` |
| --- | --- | --- |
| How | `CoreClient` owns a `tokio::runtime::Runtime`. Each method spawns its work onto it and awaits the `JoinHandle` | UniFFI wraps each future in `async_compat::Compat`, which enters a lazily created global Tokio runtime while Swift polls it |
| Where Rust code runs | Tokio's worker and blocking threads; only argument conversion and the hand-off run on the Swift thread that polls | Swift's cooperative thread pool, which has one thread per core; anything slow inside a future stalls Swift tasks |
| Control | Thread counts, names, shutdown with the client | None: one hidden global runtime |
| Blocking work | `spawn_blocking` on our runtime | `tokio::task::spawn_blocking` on the global runtime, whose context `Compat` enters while polling |
| Dependencies | `tokio` | `tokio`, `async-compat` (through UniFFI's feature) |

**Recommendation: A.** It matches what the architecture already says (the runtime is owned by
`clientmail-ffi`), keeps Rust work off Swift's small cooperative pool, and gives one place to size
and shut down threads. `JoinHandle` is an ordinary future, so any executor (Swift's, or a test's)
can await it without a Tokio context.

### The Keychain callback stays synchronous

The 1.5 note offered two fixes: call the secret store through `spawn_blocking`, or make the
callback interface async.

- `SecItem` calls are synchronous. An async Swift method would block a thread of Swift's
  cooperative pool instead of a Tokio worker: the same problem moved to a smaller pool.
- With the rule below, every call that can reach the bridge already runs on the blocking pool.

So `SecretStoreBridge` and the domain's `SecretStore` port stay synchronous. Both choices go into
decision record 0008.

### The rule

Code in `clientmail-ffi` never blocks a Tokio worker. Anything that touches SQLite or a platform
callback runs through `CoreRuntime::blocking`. Async network code (from 1.4) must run on the
workers, not in the exported method's body: UniFFI polls that body on a Swift thread with no Tokio
context. This step adds no primitive for it, since nothing uses one yet; 1.4 adds a `spawn` on the
runtime and makes `blocking` reachable from spawned tasks.

### FFI (`clientmail-ffi`)

New module `runtime.rs`:

```rust
/// The Tokio runtime the core runs on. One per `CoreClient`.
pub(crate) struct CoreRuntime { runtime: Option<tokio::runtime::Runtime> }

impl CoreRuntime {
    /// Builds a multi-thread runtime: 2 workers, at most 8 blocking threads, all drivers on,
    /// threads named "clientmail-core".
    pub(crate) fn new() -> Result<Self, CoreError>;

    /// Runs `work` on the blocking pool and waits for it from any executor.
    /// A panic inside `work` resumes as a panic in the caller.
    pub(crate) async fn blocking<T, F>(&self, work: F) -> T
    where F: FnOnce() -> T + Send + 'static, T: Send + 'static;
}

impl Drop for CoreRuntime { /* shutdown_background(): never blocks, safe inside async code */ }
```

- **Sizes.** Two workers: they will only drive network futures, which wait most of the time; the
  app aims to stay light. Eight blocking threads: SQLite is one connection behind a mutex today,
  so more threads would only queue on it, and idle blocking threads exit after Tokio's 10 s
  timeout. Both are constants in `runtime.rs`, easy to change once 1.8 measures sync.
- **Drop.** Dropping a `Runtime` normally waits for its tasks and panics when it happens inside
  async code (for example, a Rust test that drops the client in a Tokio task). `shutdown_background`
  does neither. The `Option` exists only so `Drop` can take the runtime out.
- **Panics.** A panic inside `work` comes back as a `JoinError`; `blocking` resumes it with
  `std::panic::resume_unwind`, so UniFFI reports it to Swift exactly as it does for synchronous
  calls today. A cancelled task can only come from a runtime shutdown, which cannot happen while
  callers await `blocking` before the client is dropped (every `CoreClient` method does); it
  resumes as a panic too, with an `#[expect(clippy::panic, reason = ...)]`.
- **Errors.** `Builder::build` returns an error only when a driver cannot be set up; it maps to a
  new `CoreError::Runtime` case ("the core could not start"). When the OS refuses to start a
  thread, Tokio panics instead, which reaches Swift as a panic and maps to `.storage`. Swift maps
  `.Runtime` to `.storage` too: the app shows the same "could not open" screen.

`CoreClient` changes:

```rust
pub struct CoreClient {
    runtime: CoreRuntime,
    accounts: Arc<AccountService<SqliteStore, ForeignSecretStore>>,
}

#[uniffi::export]
impl CoreClient {
    #[uniffi::constructor] pub fn open(database_path: &str, secrets: Arc<dyn SecretStoreBridge>) -> ...;   // unchanged
    #[uniffi::constructor] pub fn open_in_memory(secrets: Arc<dyn SecretStoreBridge>) -> ...;              // unchanged
    pub async fn accounts(&self) -> Result<Vec<AccountRecord>, CoreError>;
    pub async fn add_account(&self, address: String, display_name: Option<String>) -> Result<AccountRecord, CoreError>;
    pub async fn remove_account(&self, id: String) -> Result<(), CoreError>;
}
```

- The service moves behind an `Arc` because spawned work must own what it uses (`'static`): each
  method clones the `Arc` (a reference count, not the service) into the closure. Arguments become
  owned `String`s for the same reason.
- `AccountService<SqliteStore, ForeignSecretStore>` is `Send + Sync` already (`Mutex` connection,
  `Arc<dyn SecretStoreBridge + Send + Sync>`); a compile-time assertion keeps it so.
- No `async_runtime` attribute and no UniFFI `tokio` feature: the methods await a `JoinHandle`,
  which needs no Tokio context.

### Swift (`ClientMailKit/Sources/CoreAdapter`)

- `CoreCall.run` gains an async overload, `run(_ body: () async throws -> Value) async
  throws(AccountServiceError)`; the synchronous one stays for the constructors.
- `RustAccountService` methods drop `@concurrent` and `try await` the generated calls. Nothing
  blocks the caller any more: the Rust work runs on Tokio threads. Its doc comment changes to say
  so.
- `CoreError.Runtime` maps to `AccountServiceError.storage`.
- `MailDomain`, `AccountsFeature` and the app target do not change: `AccountService` was already
  `async`.

## Risks and open questions

1. **Recommendation A (own runtime) and a synchronous Keychain callback.** Approve both, or choose
   B for the runtime. B changes only `runtime.rs` and the export attributes; the Swift side is the
   same either way.
2. **Proving the callback is off the workers.** Tokio has no public "am I a worker" call, and
   workers and blocking threads share one name. The plan proves it in two halves: the runtime test
   shows a parked `blocking` call never holds a worker, and the FFI test shows the bridge runs on
   core threads at all. That every bridge call goes through `blocking` rests on code review.
3. **Notes for later steps**, added to `docs/plans/README.md` in this step (revised after the
   review):
   - 1.4: decide how async engine use cases reach the synchronous store and secret store. Suggested:
     the engine gets async ports, and adapters in `clientmail-ffi` implement them over
     `CoreRuntime::blocking`, so rules stay in the engine and blocking stays in the FFI crate.
   - 1.4: add `CoreRuntime::spawn` so async network work runs on the workers, and make `blocking`
     reachable from spawned tasks.
   - 1.4 and 1.8: cancellation needs a core-level cancel; UniFFI's Swift side has none.
   - 1.4 and 1.8: Keychain calls share the blocking pool with `SQLite`; a token read can queue
     behind store work, and a Keychain call stuck on a prompt holds a thread. Watch for it; use a
     separate pool or priority if it shows.
4. **Binary size.** Tokio with `rt-multi-thread` adds roughly a few hundred KB to the static
   library. Measured and recorded in the review log.
5. **New dependencies.** `tokio` (runtime), and `pollster` for tests only.

## Review log

### Deviations found during implementation

1. **`blocking` returns a `'static` future instead of being an `async fn`.** The work is spawned at
   the call, and the returned future does not borrow the runtime. Same behaviour for callers; it
   lets the worker test hold a parked call while it checks the worker.
2. **`CoreRuntime` keeps a `Handle` next to `Option<Runtime>`.** Spawning goes through the handle,
   so no code path has to unwrap the `Option`.
3. **No separate `Send + Sync` assertion.** Moving the `Arc` service into `spawn_blocking` already
   requires both bounds, so the compiler checks them on every method. Reversed by review finding
   C7: the assertion is back, as the plan had it.
4. **No `tokio` dev-dependency features.** The tests use `std::sync::mpsc` and a current-thread
   runtime, both covered by `rt-multi-thread`.
5. **`AccountServiceError(thrown:)`.** Both `CoreCall.run` overloads share one mapping of thrown
   errors; a Swift test covers errors that are not `CoreError`.
6. **One extra runtime test:** blocking work runs on `clientmail-core` threads.

### Checks

- Mutation check: with `blocking` changed to run the work on a worker, the one-worker test fails
  after its 5 s timeout. Restored afterwards.
- Thread check (Acceptance 3): a fresh instance of the app, sampled after 15 s idle, has exactly two
  `clientmail-core` threads and no blocking threads.
- In-app check (Acceptance 2): adding and removing accounts by hand was not done before the
  commit; the Swift integration tests exercise the same calls through the real core.
- Size: the release static library grew from 25.13 MB to 26.64 MB (+1.5 MB, unstripped archive;
  the linked app grows by less).
