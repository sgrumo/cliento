# 1.7: IMAP header fetch for the last 30 days, Gmail labels and thread ids

Status: done

## Goal

An IMAP session can open a folder read-only, find the messages that arrived in the last 30 days,
and fetch their headers, flags, size and arrival time; on Gmail also each message's id, thread id
and labels, from `[Gmail]/All Mail`. The sync engine (1.8) stores what this returns. Nothing is
visible in the app yet.

## Feature link

Roadmap M1: "fetch the last 30 days of inbox headers"; decision record 0003 (Gmail over IMAP with
`X-GM-LABELS`, `X-GM-THRID`); architecture, Identity model (a Gmail message is stored once, keyed
on `X-GM-MSGID`, with its All Mail `UID`).

## Scope

- Patched `imap-types` and `imap-codec` under `core/vendor/` with Gmail's three fetch items,
  wired through `[patch.crates-io]`.
- Domain: `SelectedMailbox`, `RemoteHeader`, `GmailItems`, `GmailLabel`, `HeaderBatch`;
  `MessageFlags` from server flags; new `MailSession` methods.
- New crate `clientmail-mime`: RFC 5322 header fields to the domain's `HeaderFields`, with
  `mail-parser`.
- `clientmail-imap`: capabilities after sign-in, `EXAMINE`, `UID SEARCH SINCE`, batched
  `UID FETCH` of headers and Gmail items.
- Transcripts, unit tests, and the opt-in Gmail test extended to fetch a few headers.

## Out of scope

- Storing anything, choosing which folders to fetch, re-matching after a `UIDVALIDITY` change,
  label-to-mailbox mapping (1.8).
- Bodies (2.1), `CONDSTORE`/`QRESYNC` and incremental fetch (2.7), threading (2.4).
- Upstreaming the Gmail patch: it needs your GitHub account and is outward-facing; offered as a
  follow-up, never done without your go-ahead.

## Design

### Gmail fetch items in a patched `imap-codec`

`imap-next` sends typed commands only, and `imap-types` models neither the Gmail items in a
`FETCH` command nor in its response, so a `FETCH` asking for `X-GM-MSGID` cannot even be built.

| | A. Patched copy under `core/vendor/` (recommended) | B. A fork on GitHub, used as a git dependency | C. Parse Gmail `FETCH` lines ourselves from the discarded bytes |
| --- | --- | --- | --- |
| How | Copy `imap-types` 2.0.0-alpha.7 and `imap-codec` 2.0.0-alpha.9 (source and licences), add the three items, `[patch.crates-io]` | Same patch in a fork under your account | `imap-next` hands back unparsable responses; a parser of our own reads them |
| In the repository | About 28 000 lines of third-party source (MIT or Apache-2.0), excluded from our lints and formatting | One line in `Cargo.toml` | Our own FETCH parser |
| Outward-facing | No | Yes: a public fork | No |
| Still cannot build the command | Fixed | Fixed | Not fixed: the `FETCH` itself cannot ask for the items |

Recommendation: A. It is the only option that is both local and complete. The patch is small and
marked (`// clientmail: Gmail`), so it can be offered upstream later (with your go-ahead) and
the copy dropped when a release has it. The vendored crates are excluded from the workspace, so
`cargo fmt`, `clippy` and our tests do not run on them; they keep their own tests.

The patch:

- `MessageDataItemName::{XGmMsgId, XGmThrId, XGmLabels}`, encoded as `X-GM-MSGID`, `X-GM-THRID`,
  `X-GM-LABELS`.
- `MessageDataItem::{XGmMsgId(u64), XGmThrId(u64), XGmLabels(Vec<GmLabel>)}` with
  `GmLabel::{System(Atom), Name(AString)}` (`\Inbox` versus `"Clients/Acme"` or a literal),
  decoded in `msg_att_static` and encoded for symmetry.
- Tests for each item, labels as atoms, quoted strings with escapes and literals included,
  through the public codecs from `clientmail-imap` (see Deviations 1).

### Domain (`clientmail-domain`)

```rust
pub struct SelectedMailbox { uid_validity: UidValidity, uid_next: Option<ImapUid>,
                             highest_modseq: Option<ModSeq>, exists: u32 }
pub enum GmailLabel { System(SystemLabel), Name(RemoteName) }   // \Inbox, \Sent, ... | a user label
pub enum SystemLabel { Inbox, Sent, Draft, Important, Starred, Trash, Spam, Other(String) }
pub struct GmailItems { message_id: GmailMessageId, thread_id: GmailThreadId, labels: Vec<GmailLabel> }
pub struct RemoteHeader { uid: ImapUid, flags: MessageFlags, header: MessageHeader,
                          gmail: Option<GmailItems> }
pub struct HeaderBatch { headers: Vec<RemoteHeader>, skipped: usize }
impl FromIterator<Flag> / MessageFlags::from_server(flags, keywords)  // note 1.1 C10
```

`MailSession` gains:

```rust
fn has_gmail_extensions(&self) -> bool;                              // X-GM-EXT-1
fn examine(&mut self, mailbox: &RemoteName) -> impl Future<Output = Result<SelectedMailbox, _>> + Send;
fn search_since(&mut self, since: UnixTime) -> impl Future<Output = Result<Vec<ImapUid>, _>> + Send;
fn fetch_headers(&mut self, uids: &[ImapUid]) -> impl Future<Output = Result<HeaderBatch, _>> + Send;
```

- `examine` is read-only (`EXAMINE`), so fetching never marks mail as read.
- `fetch_headers` asks for Gmail items when `has_gmail_extensions` is true. On Gmail the engine
  fetches from `[Gmail]/All Mail` (role `AllMail`), so `uid` is the All Mail `UID` the identity
  model needs (note 1.1 P6, P7).
- A message whose header cannot be parsed, or whose response line cannot be parsed, is skipped and
  counted; the rest of the batch is returned.

### New crate `clientmail-mime`

`parse_header_fields(raw: &[u8], received_at: UnixTime, size: u32) -> HeaderFields` with
`mail-parser` 1.0: RFC 2047 encoded words, address lists and groups (members flattened),
`Date`, `Message-ID`/`In-Reply-To`/`References` with their angle brackets (the domain strips
them), `List-Id`'s id,
`List-Unsubscribe` presence. Addresses `mail-parser` cannot read are kept as raw text, which the
domain's `Participant` already supports. Decoded subjects and names are never logged.

It is its own crate because body parsing (2.1) will live there too; it implements no port, holds
no rules, and depends on `clientmail-domain` and `mail-parser`.

### `clientmail-imap`

| Piece | Behaviour |
| --- | --- |
| Capabilities | Untagged `CAPABILITY` or a `[CAPABILITY]` code during and after `AUTHENTICATE` are kept; if none arrive, `CAPABILITY` is sent once after sign-in |
| `examine` | `EXAMINE <raw name>`; reads `UIDVALIDITY`, `UIDNEXT`, `HIGHESTMODSEQ` codes and `EXISTS`; a missing `UIDVALIDITY` is a protocol error |
| `search_since` | `UID SEARCH SINCE <date>`, the day before `since`'s UTC day: `SINCE` compares days in the server's own zone, so starting a day early misses nothing anywhere |
| `fetch_headers` | One `UID FETCH <set> (UID FLAGS INTERNALDATE RFC822.SIZE BODY.PEEK[HEADER.FIELDS (...)] [X-GM-MSGID X-GM-THRID X-GM-LABELS])` per call, the set compressed into ranges and read to its own tag; responses merged per message, only the `UID`s asked for kept. The caller pages (a few hundred `UID`s, newest first) |
| Header fields | `DATE FROM TO CC BCC REPLY-TO SUBJECT MESSAGE-ID IN-REPLY-TO REFERENCES LIST-ID LIST-UNSUBSCRIBE` |
| Flags | `\Seen`, `\Flagged`, `\Answered`, `\Draft`, `\Deleted`, `$Forwarded` to `Flag`; other keywords kept as `Keyword` when valid |
| Labels | `\Inbox`, `\Sent`, ... to `SystemLabel`; other labels as `RemoteName` (decoding to a path happens in 1.8 with the folder list) |
| Errors | As in 1.6: `NO [UNAVAILABLE]` is `Unavailable`, other refusals `Protocol`, end of file `Network`. A tagged refusal completes the command, so the session stays usable; end of file, a timeout or cancellation break it |

### Deviations found during implementation

1. **The patch is tested from `clientmail-imap`, not inside the copies.** Excluded from the
   workspace, a vendored crate run on its own builds against crates.io's unpatched `imap-types`
   and lacks `nom`'s `alloc`. Its upstream tests do run with a wrapper workspace that patches
   `imap-types` and turns on `nom/alloc` (`vendor/VENDOR.md`), which is how an upgrade is checked.
   Day to day, `tests/gmail_codec.rs` decodes, re-encodes and encodes the Gmail items through the
   public codecs, and the Gmail transcript checks them end to end. Unhooking `msg_att_gmail`
   makes both fail.
2. **No extra `CAPABILITY` after sign-in.** The session keeps the capabilities the server sends
   during or right after `AUTHENTICATE`, and otherwise the ones from before sign-in; Gmail lists
   `X-GM-EXT-1` in both, so a second round trip buys nothing.
3. **`SINCE` is quoted.** `imap-codec` writes `SINCE "26-Sep-2026"`, which RFC 3501's grammar
   allows; the transcripts follow it.
4. **`ext_condstore_qresync` is on** in `imap-next`, so `HIGHESTMODSEQ` parses. `EXAMINE` and
   `FETCH` send no CONDSTORE parameters.
5. **`fetch.rs`** holds the I/O-free parts: sequence sets, item lists, flags, labels, header
   assembly.
6. **Flags**: unknown `\`-flags and keywords that are not valid `Keyword`s are dropped;
   `$Forwarded` becomes `Flag::Forwarded`.
7. **`mail-parser` with `full_encoding`** (`encoding_rs`), so CJK and other legacy charsets
   decode before 1.8 stores headers (review C3).
8. **Licence text.** The published crates ship no licence file, so each copy gets `LICENSE-MIT`
   and `vendor/VENDOR.md` records source, version and licence.

### Deslop

Three edits by the deslop agent, no behaviour change, `make check` green:

- `fetch.rs`: `astring_bytes` and `istring_bytes` removed in favour of `imap-types`' own
  `AsRef<[u8]>`; the header bytes are borrowed instead of copied; a user label is copied only once.
- `clientmail-mime`: one `bracketed` closure for `Message-ID`, `In-Reply-To` and `References`;
  `In-Reply-To` takes the first id directly.
- `gmail_smoke.rs`: the `batch_summary` doc matches what it counts.

Left alone on purpose: the constant-list guards in `item_names` (an `expect` would add a panic),
the response loop repeated across `examine`, `search_since`, `fetch` and `list_mailboxes` (sharing
it is a new abstraction, not a cleanup), the capability `to_string()` check, and the two
`$Forwarded` checks in `message_flags` (merging them reshapes review C10's fix).
