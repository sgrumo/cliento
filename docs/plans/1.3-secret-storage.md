# 1.3: Secret storage in the Keychain

Status: done

The design below is the approved plan. The adversarial review changed parts of it; the Review log
at the end lists each change, and the code follows the log where the two differ.

## Goal

The core can save, read and delete an account's secrets (OAuth refresh tokens now, passwords
later) in the macOS Keychain, and removing an account deletes its secrets. Step 1.4 (Google
sign-in) stores its first real token through this.

## Feature link

Roadmap M1: "OAuth 2.0 with PKCE ...; tokens in the Keychain". Architecture, Storage: "Credentials
and OAuth tokens live in the macOS Keychain, never in the database". Decision record 0002
(local-first, no server of ours): the refresh token never leaves the Mac.

## The decision: where Keychain access lives

The core needs secrets without the UI (background sync refreshes tokens), so the **rules** that use
secrets live in Rust. The open question is which side talks to the Keychain.

| | A. Swift implements, Rust defines the interface (recommended) | B. Rust calls the Keychain itself |
| --- | --- | --- |
| How | A `SecretStore` port in `clientmail-domain`; Swift implements it with Apple's `SecItem` API and hands it to the core through a UniFFI callback interface | The `security-framework` or `keyring` crate calls the Keychain from Rust |
| Apple API use | First-party Swift API, the way Apple documents it; switching to the data-protection keychain later is a few attribute changes | Through third-party bindings; `keyring` uses the older file-based keychain calls |
| New Rust dependencies | `secrecy` only | `secrecy` plus `keyring` or `security-framework` (native bindings with `unsafe`) |
| Other platforms later | Each app implements one small protocol (Android Keystore, Windows Credential Manager) | `keyring` covers desktop platforms; mobile needs separate work |
| Testing | Rust tests use an in-memory fake; Swift tests use a fake keychain client; one opt-in test touches the real Keychain | Rust tests would touch the real Keychain or need a feature flag |
| Cost | A callback crosses the FFI boundary on every secret read (rare: once per token refresh) | None |

**Recommendation: A.** Swift acts as a *platform adapter*: it implements a narrow interface the core
defines and holds no rules. That keeps all rules in Rust and every Apple API in Swift. It needs one
change to the root `AGENTS.md`, recorded in decision record 0007: "Swift implements platform
services the core defines as callback interfaces (Keychain now; notifications later), with no
business rules."

The rest of this plan assumes A. If you choose B, the Swift part disappears and the FFI crate adds
`keyring` instead; the domain port and engine changes stay the same.

## Scope

- Decision record 0007 and the `AGENTS.md` / architecture wording for platform adapters.
- Domain: secret identity types and the `SecretStore` port.
- Engine: `AccountService` deletes an account's secrets when it removes the account.
- FFI: a UniFFI callback interface for secret storage, an adapter from it to the port, and
  `CoreClient` constructors that take it.
- Swift: a Keychain implementation in `CoreAdapter`, an in-memory one for previews and tests, and
  the app wiring.

## Out of scope

- OAuth sign-in, token refresh, and keeping access tokens in memory (1.4).
- Passwords for generic IMAP accounts (6.1). The types leave room for them.
- The data-protection keychain and keychain access groups: they need a team-signed app (7.2).
- Any UI. Nothing in this step is visible to the user.

## Design

### Domain (`clientmail-domain`)

```rust
pub enum SecretKind { OAuthRefreshToken }          // `Password` arrives in 6.1
impl SecretKind { pub const ALL: [Self; 1] = [Self::OAuthRefreshToken]; }

pub struct SecretKey { account: AccountId, kind: SecretKind }
impl SecretKey {
    pub const fn new(account: AccountId, kind: SecretKind) -> Self;
    pub fn label(&self) -> String;                  // "<account uuid>:oauth-refresh-token"
}

pub trait SecretStore {
    type Error: Error + Send + Sync + 'static;
    fn read(&self, key: &SecretKey) -> Result<Option<SecretString>, Self::Error>;
    fn write(&self, key: &SecretKey, secret: &SecretString) -> Result<(), Self::Error>;
    fn delete(&self, key: &SecretKey) -> Result<bool, Self::Error>;
    /// Deletes every secret of an account.
    fn delete_account(&self, account: AccountId) -> Result<(), Self::Error>;
}
```

- `SecretString` comes from the `secrecy` crate (required by `core/AGENTS.md`): its `Debug` prints
  `[REDACTED]`, it zeroes its memory on drop, and reading it needs an explicit `expose_secret()`.
- `label()` is the Keychain item's account attribute. It holds the account id, never an address,
  so a Keychain listing reveals nothing personal.
- `delete_account` deletes by iterating `SecretKind::ALL` for the account, so adding a kind later
  cannot leave a secret behind. It is a provided method on the trait, not something each adapter
  re-implements.

### Engine (`clientmail-engine`)

- `AccountService<R, S>` gains a `SecretStore`.
- `remove_account` deletes the account's secrets first, then the account row. If the secrets
  cannot be deleted, nothing is removed and the error is returned, so a token is never left behind
  for an account the user believes is gone. A secret missing for an account is fine.
- `EngineError::Secrets(source)` wraps secret-store failures; the message says only "secret
  storage failed".

### FFI (`clientmail-ffi`)

```rust
#[uniffi::export(with_foreign)]
pub trait SecretStoreBridge: Send + Sync {
    fn read(&self, label: String) -> Result<Option<String>, SecretBridgeError>;
    fn write(&self, label: String, secret: String) -> Result<(), SecretBridgeError>;
    fn delete(&self, label: String) -> Result<bool, SecretBridgeError>;
}

#[derive(uniffi::Error)]
pub enum SecretBridgeError { Unavailable, Failure { code: i32 } }
```

- `ForeignSecretStore` wraps `Arc<dyn SecretStoreBridge>` and implements the domain port. Strings
  cross the boundary as plain `String` (UniFFI has no secret type); the adapter wraps them in
  `SecretString` at once and never logs them.
- `CoreClient::open(database_path, secrets)` and `CoreClient::open_in_memory(secrets)` take the
  bridge. This changes the existing constructors; `CoreAdapter` is their only caller.
- `CoreError` gains `SecretStorage`, so Swift can tell the user the Keychain failed.
- `SecretBridgeError::Failure.code` carries the `OSStatus`, a number with no personal data.

### Swift (`ClientMailKit/Sources/CoreAdapter`)

| File | Type | Role |
| --- | --- | --- |
| `KeychainClient.swift` | `protocol KeychainClient: Sendable` | `add`, `update`, `copy`, `delete` with `[String: Any]` queries, returning `OSStatus`; the seam that tests fake |
| `SystemKeychain.swift` | `struct SystemKeychain: KeychainClient` | Calls `SecItemAdd`, `SecItemUpdate`, `SecItemCopyMatching`, `SecItemDelete` |
| `KeychainSecretStore.swift` | `final class KeychainSecretStore: SecretStoreBridge` | Builds the queries; maps `OSStatus` to `SecretBridgeError` |
| `InMemorySecretStore.swift` | `final class InMemorySecretStore: SecretStoreBridge` | For SwiftUI previews and `RustAccountService.inMemory()` |

Keychain items:

- Class `kSecClassGenericPassword`, service `dev.samuelemedici.clientmail`, account = the label.
- `kSecAttrAccessibleAfterFirstUnlock`: background sync must read tokens while the screen is
  locked, but not before the first unlock after boot.
- `kSecAttrSynchronizable` false: tokens stay on this Mac and never sync through iCloud.
- Write: `SecItemAdd`; on `errSecDuplicateItem`, `SecItemUpdate`. Read: `SecItemCopyMatching`
  with `kSecReturnData`. Delete: `SecItemDelete`; `errSecItemNotFound` returns `false`.
- `errSecInteractionNotAllowed` (keychain locked) maps to `Unavailable`; other failures to
  `Failure(code)`.
- The callbacks run on the core's threads, never the main actor; `SecItem` calls are thread-safe.

`RustAccountService.init(databaseURL:secrets:)` takes a `SecretStoreBridge`; `inMemory()` uses
`InMemorySecretStore`. The app's `Startup` passes `KeychainSecretStore(client: SystemKeychain())`.

## Risks and open questions

1. **Swift or Rust for Keychain access.** The plan recommends A (Swift implements a Rust-defined
   interface). Approve A, or choose B.
2. **File-based keychain until 7.2.** `SecItem` without the data-protection attribute uses the
   login keychain, which works for an ad-hoc-signed sandboxed app. The data-protection keychain
   needs a team-signed app with a keychain access group; switching is a note for 7.2. Items saved
   before then would need moving; acceptable while there are no users.
3. **Keychain prompts.** macOS can ask the user to allow access when an item was created by a
   differently signed build. Ad-hoc signing changes per build, so a developer may see prompts.
   Expected during development; gone with stable Developer ID signing (7.2).
4. **New dependency.** `secrecy` 0.10.

## Review log

### Deviations found during implementation

1. **`secrecy` re-exported by the domain.** `clientmail-domain` re-exports `SecretString` and
   `ExposeSecret`, so the engine and FFI crates use the domain's types without depending on
   `secrecy` themselves. One version, one place.
2. **`SecretBridgeError::Unexpected`.** UniFFI requires every foreign-trait error to convert from
   `UnexpectedUniFFICallbackError` (an error the foreign code throws that the interface does not
   declare). It maps to this new case instead of overloading `Failure { code }`.
3. **Swift shows the new error.** `AccountServiceError.secretStorage`, its mapping in
   `CoreAdapter`, and a localised message in `AccountsFeature` ("ClientMail could not use the
   Keychain. Unlock your Mac and try again."). The plan said Swift could tell the user; this is
   how.
4. **`tempfile` for the FFI integration tests.** The reopen test now uses a temporary folder that
   removes itself.
5. **The fake Keychain records a summary.** Strict concurrency rejects storing `[String: Any]` in
   a `Mutex`, so the fake keeps a small `Sendable` struct of the attributes the tests check.

### Adversarial review

The user approved every recommendation below. "Fixed" means changed in this step; "noted" means
recorded for a later step in `docs/plans/README.md`; "user check" means the user verifies it in
the app before deslop.

**Plan findings**

| # | Severity | Finding | Decision |
| --- | --- | --- | --- |
| P1 | major | A token written during a removal outlives its account | Noted for 1.4: writes and removal of one account never overlap |
| P2 | major | A Keychain that keeps failing blocks every removal | Noted for 1.4: block only on `Unavailable`, otherwise remove and retry the deletion later |
| P3 | minor | In the login keychain, "locked" likely prompts instead of failing; accessibility classes have no effect there | Noted for 1.4: no UI on background reads; verify the real locked status |
| P4 | minor | Docs overstated zeroing of secrets | Fixed: decision record 0007 and the adapter comment say only Rust's copy is zeroed |
| P5 | minor | Keychain calls block and would stall Tokio workers | Noted for 1.5: `spawn_blocking` or an async callback |
| P6 | minor | No way to find orphaned items | Noted for 1.4: insert before writing the token; plan a sweep |
| P7 | minor | Nothing confirms the sandboxed, ad-hoc-signed app can delete items | User check: done, removal works in the built app |
| P8 | minor | Items could migrate to another Mac, against decision record 0002 | Fixed: `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` |
