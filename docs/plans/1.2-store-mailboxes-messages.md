# 1.2: Store: mailboxes and messages tables, body file store

Status: done

The design below is the approved plan. The adversarial review changed parts of it; the Review log
at the end lists each change, and the code follows the log where the two differ.

## Goal

The core can persist the mailboxes of an account, their sync position, and message headers with
their flags, labels and server identity, and can read one page of a mailbox's message list. Message
bodies and attachments get a content-addressed file store. Nothing syncs yet: step 1.8 writes, step
1.11 reads.

## Feature link

Roadmap M1 ("see the inbox within 5 seconds, quit offline and still read it"): this is the
"still read it offline" half. Architecture: Storage and Identity model sections. Decision record
0004 (SQLite, bodies on disk).

## Notes carried over from the 1.1 review

Every note listed for 1.2 in `docs/plans/README.md` is resolved by this plan:

| Note | Where it is resolved |
| --- | --- |
| P9: `Message` aggregate and mailbox sync state belong in the domain | Design, "Domain additions" |
| P9: for plain IMAP, `RemoteMessageRef::Imap.mailbox` is the source of truth; labels only for Gmail | Design, "Schema" (`messages.mailbox_id`, `message_labels`) |
| P10: mailboxes keyed on `MailboxId`, not `(account, path)` | Design, "Schema" (`mailboxes.id` primary key, path updatable) |

## Scope

- Domain additions: `Message`, `MailboxSyncState`, `ModSeq`, `BlobId`, and three port traits.
- Migration 2: tables for mailboxes, messages, participants, references, keywords and Gmail labels.
- `SqliteStore` implements the mailbox and message ports.
- `FileBlobStore`: content-addressed files for message bodies, with atomic writes.
- Decision record 0006 for the message table layout; architecture doc updated.

## Out of scope

- Any sync logic: matching server messages, handling a changed `UIDVALIDITY`, detecting expunges
  (1.8, 2.7).
- Changing flags or deleting messages after they are stored (2.5, 2.7).
- Linking a body blob to a message, MIME parsing, and sweeping orphan blobs (2.1).
- Full-text search tables (4.1).
- A connection pool with separate readers and writer (1.8, when sync writes run next to UI reads).
- Exposing mailboxes or messages through UniFFI or Swift (1.9, 1.11).

## Design

### Domain additions (`clientmail-domain`)

| Item | Shape | Why |
| --- | --- | --- |
| `ModSeq` | `NonZeroU64`, `new(u64) -> Option<Self>`, `get()` | CONDSTORE `HIGHESTMODSEQ`. RFC 7162 limits it to 1..2^63-1, so it fits SQLite's `INTEGER` as is |
| `MailboxSyncState` | `uid_validity: UidValidity`, `uid_next: Option<ImapUid>`, `highest_modseq: Option<ModSeq>` | Where incremental sync resumes. `uid_next` and `highest_modseq` are optional because servers may omit them |
| `Message` | `id`, `account_id`, `remote: RemoteMessageRef`, `header: MessageHeader`, `flags: MessageFlags`; `new(..)` with those five arguments, and accessors | The aggregate every layer passes around (review note P9) |
| `BlobId` | `[u8; 32]` SHA-256, `Display` as lowercase hex, `FromStr` | Names a stored body by its content |
| `Flag::ALL` | `[Flag; 6]` | Lets storage map every flag to its own column bit without knowing the in-memory layout |

`Message` has five fields, the limit for a constructor, so it takes them directly. `Debug` is
derived: every field already redacts its own personal data.

### Ports (`clientmail-domain::ports`)

Only what steps 1.8 (initial sync) and 1.11 (message list) need:

```rust
pub trait MailboxRepository {
    type Error: Error + Send + Sync + 'static;
    fn mailboxes(&self, account: AccountId) -> Result<Vec<Mailbox>, Self::Error>;
    fn upsert_mailbox(&self, mailbox: &Mailbox) -> Result<(), Self::Error>;
    fn delete_mailbox(&self, id: MailboxId) -> Result<bool, Self::Error>;
    fn sync_state(&self, id: MailboxId) -> Result<Option<MailboxSyncState>, Self::Error>;
    fn set_sync_state(&self, id: MailboxId, state: &MailboxSyncState) -> Result<(), Self::Error>;
}

pub trait MessageRepository {
    type Error: Error + Send + Sync + 'static;
    /// Inserts new messages and updates header and flags of known ones, in one transaction.
    /// Returns the stored id of each message, in input order.
    fn upsert_messages(&self, messages: &[Message]) -> Result<Vec<MessageId>, Self::Error>;
    fn set_labels(&self, id: MessageId, labels: &[MailboxId]) -> Result<(), Self::Error>;
    fn message(&self, id: MessageId) -> Result<Option<Message>, Self::Error>;
    fn page(&self, query: &PageQuery) -> Result<Vec<Message>, Self::Error>;
}

pub trait BlobStore {
    type Error: Error + Send + Sync + 'static;
    fn put(&self, bytes: &[u8]) -> Result<BlobId, Self::Error>;
    fn get(&self, id: BlobId) -> Result<Option<Vec<u8>>, Self::Error>;
}
```

- `PageQuery`: `mailbox: MailboxId`, `limit: u32`, `before: Option<PageCursor>`.
  `PageCursor` is `(UnixTime, MessageId)`: keyset pagination on `received_at` descending, with
  the id breaking ties. Offsets would slow down with every page; a cursor does not.
- **Identity on upsert.** A message is "known" when a row has the same remote key: `(mailbox,
  UIDVALIDITY, UID)` for plain IMAP, `(account, X-GM-MSGID)` for Gmail. The stored row keeps its
  original `MessageId`, which is why `upsert_messages` returns the ids. This is a storage
  constraint (a unique key), not a sync rule: deciding what to do when `UIDVALIDITY` changes stays
  in 1.8.

### Schema (migration 2)

All tables `STRICT`. Foreign keys cascade on delete, so removing an account removes its mail.

```sql
CREATE TABLE mailboxes (
    id TEXT PRIMARY KEY NOT NULL,
    account_id TEXT NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    path TEXT NOT NULL,
    delimiter TEXT CHECK (delimiter IS NULL OR length(delimiter) = 1),
    role TEXT NOT NULL CHECK (role IN ('inbox', 'all-mail', 'archive', 'drafts', 'sent',
                                       'trash', 'junk', 'starred', 'important', 'custom')),
    selectable INTEGER NOT NULL CHECK (selectable IN (0, 1)),
    uid_validity INTEGER,
    uid_next INTEGER,
    highest_modseq INTEGER,
    UNIQUE (account_id, path)
);

CREATE TABLE messages (
    id TEXT PRIMARY KEY NOT NULL,
    account_id TEXT NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    remote_kind TEXT NOT NULL CHECK (remote_kind IN ('imap', 'gmail')),
    mailbox_id TEXT REFERENCES mailboxes(id) ON DELETE CASCADE,  -- imap only
    uid_validity INTEGER NOT NULL,                                -- imap: mailbox; gmail: All Mail
    uid INTEGER NOT NULL,
    gmail_message_id INTEGER,                                     -- gmail only, u64 bits
    gmail_thread_id INTEGER,                                      -- gmail only, u64 bits
    subject TEXT,
    sent_at INTEGER,
    received_at INTEGER NOT NULL,
    header_message_id TEXT,
    in_reply_to TEXT,
    list_id TEXT,
    has_list_unsubscribe INTEGER NOT NULL CHECK (has_list_unsubscribe IN (0, 1)),
    size_bytes INTEGER NOT NULL,
    flags INTEGER NOT NULL,
    CHECK ((remote_kind = 'imap' AND mailbox_id IS NOT NULL
            AND gmail_message_id IS NULL AND gmail_thread_id IS NULL)
        OR (remote_kind = 'gmail' AND mailbox_id IS NULL
            AND gmail_message_id IS NOT NULL AND gmail_thread_id IS NOT NULL))
);
CREATE UNIQUE INDEX messages_imap_key ON messages (mailbox_id, uid_validity, uid)
    WHERE remote_kind = 'imap';
CREATE UNIQUE INDEX messages_gmail_key ON messages (account_id, gmail_message_id)
    WHERE remote_kind = 'gmail';
CREATE INDEX messages_mailbox_list ON messages (mailbox_id, received_at DESC, id DESC);
CREATE INDEX messages_header_message_id ON messages (header_message_id);
CREATE INDEX messages_gmail_thread ON messages (account_id, gmail_thread_id);

CREATE TABLE message_participants (
    message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    field TEXT NOT NULL CHECK (field IN ('from', 'to', 'cc', 'bcc', 'reply-to')),
    position INTEGER NOT NULL,
    name TEXT,
    address TEXT NOT NULL,
    address_valid INTEGER NOT NULL CHECK (address_valid IN (0, 1)),
    PRIMARY KEY (message_id, field, position)
) WITHOUT ROWID;
CREATE INDEX message_participants_address ON message_participants (address COLLATE NOCASE);

CREATE TABLE message_references (
    message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    position INTEGER NOT NULL,
    header_message_id TEXT NOT NULL,
    PRIMARY KEY (message_id, position)
) WITHOUT ROWID;

CREATE TABLE message_keywords (
    message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    keyword TEXT NOT NULL,
    PRIMARY KEY (message_id, keyword)
) WITHOUT ROWID;

CREATE TABLE message_labels (
    message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    mailbox_id TEXT NOT NULL REFERENCES mailboxes(id) ON DELETE CASCADE,
    PRIMARY KEY (message_id, mailbox_id)
) WITHOUT ROWID;
CREATE INDEX message_labels_mailbox ON message_labels (mailbox_id, message_id);
```

Why these choices:

- **Participants in their own table**, not JSON: Smart Inbox (5.1) asks "has the user written to
  this address?" and search (4.1) filters by sender. Both need an index on the address.
- **References in their own table**: threading (2.4) looks messages up by id; the table keeps
  order with `position` and needs no separator that an id could contain.
- **One `messages` row per message, with a kind column and a `CHECK`**: both remote shapes share
  `uid_validity` and `uid` (for Gmail they are the All Mail values), so the table stays narrow and
  the `CHECK` rejects half-filled rows.
- **Plain IMAP mailbox in `messages.mailbox_id`**, labels only for Gmail (note P9). The message
  list query reads `messages.mailbox_id` for IMAP mailboxes and `message_labels` for Gmail ones.
- **`UNIQUE (account_id, path)`** stays: two folders cannot share a name at the same time. But
  the primary key is `id`, and `upsert_mailbox` updates the path of an existing id, so a rename
  is an update, not a delete plus insert (note P10).
- **Flags as one integer** with a storage-owned bit per `Flag` (built from `Flag::ALL`), so the
  in-memory layout can change without a migration. Keywords are rare and get their own table.
- **Gmail's All Mail**: every Gmail message is in it, but `X-GM-LABELS` never lists it. The sync
  engine (1.8) adds the All Mail mailbox to each message's labels so the list query stays uniform.
  This is a note for 1.8, not store logic.

### Gmail ids in SQLite (note P12)

`GmailMessageId` and `GmailThreadId` cover the full `u64` range. They are written with
`u64::cast_signed` and read with `i64::cast_unsigned`, which keep the bits and never fail. A test
round-trips `u64::MAX` and `2^63`.

### Writes

- `upsert_messages` runs in one transaction. For each message it upserts the row on the remote
  key (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING id`), then replaces its participants,
  references and keywords. Statements are prepared once per call with `prepare_cached`.
- The existing `with_connection` gives `&Connection`. Transactions use
  `Connection::unchecked_transaction`, which works through a shared reference; the `Mutex` already
  guarantees no other transaction runs at the same time.
- Target: 10,000 headers in under 2 seconds in a release build on Apple Silicon.

### Blob store (`clientmail-store::FileBlobStore`)

- Root folder next to the database (`.../ClientMail/blobs/`), chosen by the caller.
- File name: SHA-256 of the content in hex, split as `ab/cdef...` so no folder holds more than a
  few thousand files.
- `put` hashes, returns early when the file exists, otherwise writes to a temporary file in the
  same folder and renames it into place. A crash never leaves a half-written blob under its final
  name.
- `get` reads the file and checks its hash; a mismatch is `StoreError::CorruptBlob`, not silent
  bad data.
- Content-agnostic: step 2.1 decides whether it stores the raw message or parsed parts.

### Errors

`StoreError` gains `Io(std::io::Error)` for blob files and `CorruptBlob`. Messages never include
paths or content.

## Risks and open questions

1. **New dependencies.** `sha2` and `tempfile` (dev only). Approve, or prefer another hash (for
   example `blake3`, faster but larger)?
2. **Upsert keeps the first id.** Callers must use the ids `upsert_messages` returns, not the ids
   they generated. Documented on the trait and tested.
3. **`UIDVALIDITY` change.** Rows with the old value stay until 1.8 decides to drop or re-match
   them. The unique key includes `uid_validity`, so old and new rows can coexist meanwhile.
4. **One connection.** Sync writes and UI reads share a `Mutex` until the pool arrives (1.8). A
   10,000-message upsert holds the lock for its transaction, up to the 2-second budget.

## Review log

### Deviations found during implementation

1. **`StoreError::MissingMailbox`.** The plan gave `set_sync_state` no error for an unknown
   mailbox. A silent no-op would hide sync bugs, so it returns this new variant; the trait docs say
   so and a test covers it.
2. **`DomainError::InvalidBlobId`.** `BlobId: FromStr` needed an error; added as a variant and
   mapped to `CoreError::Storage` in the FFI crate.
3. **`HeaderMessageId::parse` fallback.** A stored id is read back by wrapping it in angle brackets
   and parsing it again. The fallback for headers without brackets could keep a word containing
   `<` or `>` (`a>b@x`), which would not survive that round trip. Such words are now dropped, so
   every stored id round-trips exactly. One test case added in `clientmail-domain`.
4. **Migrations as `.sql` files.** The schema is long, so both migrations now live in
   `clientmail-store/migrations/` and are embedded with `include_str!`. Migration 1's SQL is
   unchanged.
5. **Page loading.** Each page loads child rows with one query per child table per message. Noted
   for 1.11 to measure.
6. **Performance measurement.** The ignored test runs on an in-memory database: about 0.36 s for
   10,000 messages in release on Apple Silicon (budget 2 s). A database file in WAL mode will be
   slower; not measured in this step.

### Adversarial review

The user approved every recommendation below. "Fixed" means changed in this step; "noted" means
recorded for a later step in `docs/plans/README.md`; "dropped" means removed.

**Plan findings**

| # | Severity | Finding | Decision |
| --- | --- | --- | --- |
| P1 | major | No way to keep a `MessageId` when its server key changes (`UIDVALIDITY`, moves); a re-keyed upsert failed the whole batch | Fixed: upsert matches on `id` first and rewrites the server key; tests for re-keying and moves; 1.8 note rewritten |
| P2 | major | A future table rebuild in a migration would cascade-delete child rows, because `PRAGMA foreign_keys` is ignored inside a transaction | Fixed: `migrate` turns foreign keys off around each migration and runs `foreign_key_check` before commit; rule documented; rebuild and violation tests |
| P3 | major | Gmail label pages sorted the whole label each time; the `?2 IS NULL OR` cursor stopped index seeks | Fixed: `message_labels.received_at` with a list index; separate first-page and next-page statements per source; merged in Rust; a query-plan test asserts no sort step |
| P4 | minor | Pages returned `\Deleted` messages | Fixed: both sources skip them; test that the page still fills |
| P5 | minor | Labels could be set on IMAP messages, listing them twice | Fixed: `set_labels` returns `LabelsOnImapMessage` (and `MissingMessage` for unknown ids) |
| P6 | minor | No stable integer key for FTS5 | Fixed: `seq INTEGER PRIMARY KEY`, `id TEXT UNIQUE` |
| P7 | minor | Swapping folder names hits the unique path constraint | Noted for 1.8 |
| P8 | minor | Messages and labels are written in separate transactions | Noted for 1.8: save sync state last |

**Code findings**

| # | Severity | Finding | Decision |
| --- | --- | --- | --- |
| C1 | minor | Untested: Gmail key update, label page with cursor, folder isolation; one test could not fail | Fixed: those tests added; the non-failing test replaced by "same key twice in one batch" |
| C2 | minor | `BlobId` accepted a leading `+` | Fixed: every character must be a hex digit |

### Deslop

Nine cleanups, no behaviour change, `make check` green:

- `message_rows.rs`: `fields_without_participants` moved into the single `impl MessageRow`; the
  two copies of "wrap a stored id in `<...>`" became one `bracketed` helper; a closure used once in
  `build_remote` replaced by the error written out, like the rest of the function.
- `messages.rs`: `set_labels` converts the id to text once instead of once per statement and label.
- `mailboxes.rs`: `sync_state` builds the state inside its `and_then`, dropping a tuple and a
  `.map`; the `MailboxColumns` doc now mentions its `bool` column.
- `blobs.rs`: a test binds the temporary folder as `_folder` instead of dropping it by hand.
- `sync.rs`: a comment explains why `ModSeq::new` spells out `Option::map` as a `match` (`const fn`).

Left alone on purpose: shared helpers for the repeated `UIDVALIDITY`/`UID` parsing and the
corrupt-row closure (new abstractions), a `MailboxRole::ALL` constant (domain API change), the
repeated SQL fragments in the query-plan test, and the `u64` column helpers (they name the encoding
and are tested).
