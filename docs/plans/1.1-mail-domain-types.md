# 1.1: Domain types for mailboxes and message headers

Status: draft

## Goal

`clientmail-domain` can describe a mailbox and the header of a message for any account, so the
store (1.2), the IMAP crate (1.6, 1.7) and the sync engine (1.8) share one vocabulary. No storage,
network or UI changes yet.

## Feature link

Roadmap M1 ("see the inbox"): the message list needs sender, subject, date, read state and the
mailbox a message is in. Threading (2.4) and Smart Inbox (5.1) build on the identity and header
fields defined here.

## Scope

- Value types for mailboxes, message identity, message headers, participants, flags and time.
- Validation and normalisation rules for those types, with unit tests.
- One shared way to define UUID-backed ids, reused by `AccountId`.

## Out of scope

- Repository traits and SQL tables for mailboxes and messages: step 1.2, together with the store
  that implements them.
- Parsing IMAP responses, Modified UTF-7 folder names, RFC 5322 dates and `SPECIAL-USE`
  attributes: step 1.6 and 1.7. The domain receives already-decoded values.
- Exposing these types through UniFFI and Swift: step 1.9 and 1.11, when the UI first needs them.
- Body, MIME structure, attachments, preview text: step 2.1.
- Subject normalisation (`Re:`, `Fwd:`) and thread grouping: step 2.4.
- `List-Unsubscribe` and other headers used for Smart Inbox: step 5.1.
- Microsoft Graph message identity: step 6.5.

## Design

All new code lives in `core/crates/clientmail-domain`. No new crates, no new dependencies.

### Identifiers

- `MailboxId` and `MessageId`: local UUID v7 ids, like `AccountId`. Local ids never change, even
  when a server renumbers its messages, so the store and the UI can key on them.
- The `uuid_id!` macro removes the duplication three hand-written id types would have. It takes the
  type name, its doc comment and the `DomainError` variant to return on bad input.

### Time

`UnixTime`: seconds since the Unix epoch, UTC, as `i64`. Ordered, `Copy`.

- Only the core compares and orders times; Swift formats them with `FormatStyle`.
- The sender's time zone is not needed for any feature in the roadmap.
- **Alternative:** the `jiff` crate gives calendar arithmetic and formatting. Rejected for now: the
  domain only needs ordering and "older than N days", which a newtype covers. If calendar logic
  arrives (send later at "tomorrow 9:00"), adopt `jiff` then with a decision record.

### Mailboxes

```rust
pub struct Mailbox {
    id: MailboxId,
    account_id: AccountId,
    path: MailboxPath,
    role: MailboxRole,
    selectable: bool,
}
```

- `MailboxPath`: the server's folder name, already decoded to Unicode, plus its hierarchy delimiter
  (`/` or `.`, or none). Methods: `as_str`, `segments()`, `leaf_name()`, `parent()`.
  Validation: not empty, no control characters, no empty segment.
- `MailboxRole`: `Inbox`, `Archive`, `Drafts`, `Sent`, `Trash`, `Junk`, `Starred`, `Important`,
  `Custom`. The IMAP crate maps `SPECIAL-USE` attributes and Gmail's `\Important` onto it; the
  domain does not know protocol strings.
- `selectable`: false for folders that only group other folders (IMAP `\Noselect`).
- Display names come from `leaf_name()`, or from the role for system folders (UI step).

### Message identity

```rust
pub enum RemoteMessageRef {
    Imap { mailbox: MailboxId, uid_validity: UidValidity, uid: ImapUid },
    Gmail { message_id: u64 },
}
```

- Plain IMAP identifies a message by mailbox, `UIDVALIDITY` and `UID`. When `UIDVALIDITY` changes,
  every UID in that mailbox is invalid, which is why it is part of the reference.
- Gmail exposes one stable id per message (`X-GM-MSGID`) across all labels, so a message in three
  labels is one message, not three copies.
- `ImapUid` and `UidValidity` wrap `NonZeroU32`, because 0 is not a valid value in IMAP.
- Which mailboxes a message belongs to is a relation stored in step 1.2, not a field of the header.

### Participants

Real-world headers contain addresses that are not RFC-valid (`undisclosed-recipients:;`, missing
domains, broken encodings). Rejecting them would hide mail, so:

```rust
pub struct Participant { name: Option<String>, address: ParticipantAddress }
pub enum ParticipantAddress { Valid(EmailAddress), Unparsed(String) }
```

- `Participant::new(name, raw_address)` tries `EmailAddress::parse` and falls back to `Unparsed`.
- Empty or whitespace names become `None`. A name equal to the address becomes `None`.
- `display_name()` returns the name, else the address text.

### Flags

```rust
pub struct MessageFlags {
    seen: bool, flagged: bool, answered: bool, draft: bool, forwarded: bool,
    keywords: BTreeSet<Keyword>,
}
```

- The five booleans cover the system flags plus `$Forwarded`, which every list view needs.
- `Keyword`: any other IMAP keyword, validated as an IMAP atom (no spaces, no `(){%*"\]`, no control
  characters). Custom ClientMail keywords (snooze, smart inbox) arrive in M5 and reuse this type.
- `BTreeSet` keeps keywords sorted and unique, so equal flag sets compare equal.

### Header

`MessageHeader` has more than five fields, so it is built from a parameter object:

```rust
pub struct HeaderFields {          // plain input, public fields
    pub subject: Option<String>,
    pub from: Vec<Participant>,
    pub to: Vec<Participant>,
    pub cc: Vec<Participant>,
    pub reply_to: Vec<Participant>,
    pub sent_at: Option<UnixTime>,
    pub received_at: UnixTime,
    pub message_id: Option<String>,
    pub in_reply_to: Option<String>,
    pub references: Vec<String>,
    pub size_bytes: u32,
}

impl MessageHeader {
    pub fn from_fields(fields: HeaderFields) -> Self;   // normalises, never fails
    // accessors for every field, plus:
    pub fn sort_time(&self) -> UnixTime;                // sent_at if plausible, else received_at
}
```

Normalisation in `from_fields`:

- Subject: trimmed; empty becomes `None`.
- `message_id`, `in_reply_to`, `references`: angle brackets and whitespace removed; empty values
  dropped; duplicate references removed keeping the first occurrence. These feed threading in 2.4.
- `sort_time`: `sent_at` when present and not more than one day after `received_at`, otherwise
  `received_at`. Senders with wrong clocks must not pin mail to the top of the list.

`from_fields` cannot fail: a header is what the server sent, and the client must show it anyway.

### Errors

New `DomainError` variants: `InvalidMailboxId`, `InvalidMessageId`, `InvalidMailboxPath { reason }`,
`InvalidKeyword`. Messages never include the offending value, because it can be personal data.

### Layer check

Everything is pure data and validation, so it belongs in `clientmail-domain`. Nothing here touches
I/O, and no other crate changes except `clientmail-ffi`'s exhaustive `match` on `DomainError`,
which gains the new variants (mapped to the existing `CoreError` cases until Swift needs them).

## Risks and open questions

1. **Gmail versus plain IMAP identity.** Gmail accounts use `RemoteMessageRef::Gmail`; every other
   IMAP account uses `Imap`. A Gmail account switched to plain IMAP mode is out of scope.
2. **`u32` size.** Messages over 4 GiB cannot exist on any provider we target (Gmail's limit is
   25 MB sent, 50 MB received), so `u32` is enough.
3. **Plausible `sent_at` window.** One day of tolerance is a guess. Do you want a different value,
   or no correction at all?
4. **Bcc.** Left out: servers only expose it on messages you sent, and drafts get it in step 3.1.
