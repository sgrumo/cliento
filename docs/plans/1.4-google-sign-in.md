# 1.4: Google sign-in with PKCE, tokens saved and refreshed

Status: done

The design below is the approved plan. Implementation and the adversarial review changed parts of
it (for example `parse_callback` now checks the state, and grants carry `mail_access`); the Review
log at the end lists each change, and the code follows the log where the two differ.

## Goal

The user adds a Gmail or Google Workspace account by signing in with Google in a browser sheet.
The core exchanges the code for tokens, creates the account from the identity Google returns,
saves the refresh token in the Keychain, and can hand out a fresh access token on demand (IMAP
uses it from 1.6). Signing in again with the same account replaces its token.

## Feature link

Roadmap M1: "OAuth 2.0 with PKCE through `ASWebAuthenticationSession`; tokens in the Keychain".
Decision record 0003 (Gmail signs in with OAuth 2.0 / XOAUTH2) and 0002 (no server of ours: tokens
go only between the Mac and Google).

## Scope

- Domain: OAuth value types, an `OAuthClient` port, a `Blocking` port, a `Clock` port, and a way to
  create an account with a known provider.
- New crate `clientmail-oauth`: Google's authorization URL, callback parsing, token exchange and
  refresh over HTTPS, ID token claims.
- Engine: `GoogleSignIn` and `TokenService` use cases, per-account locks, `remove_account` under
  the lock and clearing cached tokens.
- FFI: `CoreRuntime::spawn`, the `Blocking` and `Clock` adapters, a `GoogleSignInSession` object
  with `complete` and `cancel`, the Google client id at `open`, new `CoreError` cases.
- Swift: Keychain reads that never show UI; sign-in in `MailDomain`, `CoreAdapter` and the Accounts
  sheet; the client id from a gitignored xcconfig.
- Docs: decision records 0009 (blocking port) and 0010 (HTTP and TLS), architecture, `AGENTS.md`
  crate table, Google Cloud setup in a short `docs/google-oauth.md`.

## Out of scope

- Pending deletions and the orphaned-item sweep (new step 1.12, see Risks 3).
- Using the access token: XOAUTH2 in IMAP (1.6). `TokenService` is built and tested in the engine
  now; the FFI wires it in 1.6, when something calls it (an unused field would be dead code).
- Showing "sign in again" on an account whose refresh token stopped working. The engine returns
  `SignInRequired`; the account list shows it from 1.10.
- Microsoft sign-in (6.4); passwords for other providers (6.1). The manual add form stays for them.
- Choosing a sender name in the UI. The name from Google's `profile` scope fills `display_name`.
- Publishing the Google OAuth app (verification of the restricted `mail.google.com` scope). It stays
  in Testing mode until release (7.x).

## Design

### Flow

```
Accounts sheet         CoreAdapter / FFI                   Engine / oauth crate          Google
--------------         -----------------                   --------------------          ------
"Sign in with Google" -> begin_google_sign_in() ---------> GoogleSignIn::begin
                                                          (PKCE verifier + state, URL)
WebAuthenticationSession(url, scheme, .ephemeral) ------------------------------------> consent
        <------------------------------------------- callback URL (code, state) ------
session.complete(callback) -> spawn on workers -------> parse, check state
                                                          exchange code (async HTTPS) --> token
                                                          blocking: lock, insert row,
                                                          write refresh token
        <------------- AccountRecord -----------------
```

Cancelling (closing the browser, or the sheet while `complete` runs) calls `session.cancel()`,
which aborts the spawned task. Nothing is stored before the code exchange finishes, and the
store-and-Keychain part runs as one blocking closure that an abort cannot split (see Cancellation).

### Domain (`clientmail-domain`)

New module `oauth.rs`. Types that hold a secret wrap `SecretString`; types with personal data
redact `Debug`.

```rust
pub struct PkceVerifier(SecretString);      // 43-128 unreserved characters (RFC 7636)
pub struct OAuthState(String);              // opaque, random; compared to the callback's
pub struct AuthorizationCode(SecretString);

pub struct AuthorizationRequest { url: String, state: OAuthState, verifier: PkceVerifier }
pub struct CallbackParams { code: AuthorizationCode, state: OAuthState }

pub struct AccessToken { token: SecretString, expires_at: UnixTime }
pub struct OAuthIdentity { email: EmailAddress, name: Option<String> }   // Debug redacts both
pub struct TokenGrant {
    access: AccessToken,
    refresh: Option<SecretString>,          // Google sends it on sign-in; usually not on refresh
    identity: Option<OAuthIdentity>,        // from the ID token; sign-in only
}

pub enum OAuthErrorKind {
    Denied,     // the user refused consent (`error=access_denied` in the callback)
    Rejected,   // the server refused the grant (`invalid_grant`): sign in again
    Network,    // no connection, timeout, TLS failure
    Protocol,   // anything malformed or unexpected
}
```

Ports in `ports.rs`:

```rust
/// One OAuth provider's protocol. Implemented by `clientmail-oauth`.
pub trait OAuthClient: Send + Sync + 'static {
    type Error: Error + Send + Sync + 'static;
    fn error_kind(error: &Self::Error) -> OAuthErrorKind;
    /// A fresh verifier and state, and the URL to open.
    fn authorization(&self) -> AuthorizationRequest;
    /// The scheme the browser sheet waits for.
    fn callback_scheme(&self) -> &str;
    fn parse_callback(&self, url: &str) -> Result<CallbackParams, Self::Error>;
    fn exchange(&self, code: AuthorizationCode, verifier: PkceVerifier)
        -> impl Future<Output = Result<TokenGrant, Self::Error>> + Send;
    fn refresh(&self, refresh_token: SecretString)
        -> impl Future<Output = Result<TokenGrant, Self::Error>> + Send;
}

/// Runs synchronous work (storage, platform callbacks) where it cannot block async tasks.
pub trait Blocking: Send + Sync + 'static {
    fn run<T, F>(&self, work: F) -> impl Future<Output = T> + Send + 'static
    where F: FnOnce() -> T + Send + 'static, T: Send + 'static;
}

pub trait Clock: Send + Sync + 'static {
    fn now(&self) -> UnixTime;
}
```

- `async fn` in a public trait cannot promise its future is `Send`, which Tokio needs; returning
  `impl Future + Send` states it. Callers are generic, so this costs no boxing.
- Random values (verifier, state) come from the oauth crate: the domain does no I/O, and reading the
  OS's random source is I/O.
- `NewAccount::into_account_with(provider)` creates an account with a known provider. Signing in
  with Google makes a `Provider::Gmail` account even on a Workspace domain, which `Provider::detect`
  cannot recognise.

### Decision record 0009: async use cases reach synchronous ports through `Blocking`

| | A. `Blocking` port (recommended) | B. Async twins of every port | C. Engine depends on Tokio |
| --- | --- | --- | --- |
| How | The engine wraps each storage or secret call in `blocking.run(...)`; the FFI implements `Blocking` with `CoreRuntime` | `AsyncAccountRepository`, `AsyncSecretStore`, ...; the FFI adapts each sync port | The engine calls `tokio::task::spawn_blocking` itself |
| New code | One small trait and one adapter | One trait and one adapter per port, growing with every port | None |
| Engine rules | Unchanged: engine depends on the domain only | Unchanged | The engine gains a runtime dependency; tests need a runtime |
| Tests | A fake that runs the work inline | Fakes for every async twin | A Tokio runtime per test |

Recommendation: A. The engine keeps every rule and stays runtime-free; the only cost is that ports
used inside `run` must be shared (`Arc`), because the work runs on another thread. Synchronous use
cases (`AccountService` today) stay synchronous and keep running inside `CoreRuntime::blocking` from
the FFI, as now. Decision record 0008 is updated to point here.

### Engine (`clientmail-engine`)

**Shared state.** `AccountService`, `GoogleSignIn` and `TokenService` share, through `Arc`, the
account repository, the secret store, an `AccountLocks` and a `TokenCache`.

- `AccountLocks` (crate-private): one `std::sync::Mutex<()>` per account id, created on first use.
  Every write of an account's token, and its removal, runs inside `with_lock(account, || ...)`.
  The lock is a plain (not async) mutex and is only ever taken inside `Blocking::run` work, so it
  never blocks a Tokio worker. Removal drops the account's entry.
- `TokenCache` (crate-private): `Mutex<HashMap<AccountId, AccessToken>>`, in memory only.

**`AccountService::remove_account`** takes the account lock around "delete secrets, delete row" and
clears the cached access token. Behaviour is otherwise unchanged.

**`GoogleSignIn<O, R, S, B>`**

- `begin() -> PendingSignIn`: asks the port for a verifier, state and URL. `PendingSignIn` holds the
  verifier and state; nothing is stored.
- `complete(pending, callback_url) -> Result<Account, EngineError>` (async):
  1. `parse_callback`; a `Denied` error becomes `EngineError::SignInDenied`.
  2. The callback's state must equal the pending state, or `SignInFailed`.
  3. `exchange` (async). The grant must carry an identity and a refresh token, or `SignInFailed`.
     The identity's address must be verified (`email_verified` in the ID token, checked in the
     oauth crate).
  4. In one `Blocking::run` closure, under the account's lock:
     - no account with this address: insert a `Gmail` account, then write the refresh token; if the
       write fails, delete the row and return the secret error (note P6: row first, never a token
       without a row);
     - a `Gmail` account with this address: write the new refresh token (signing in again);
     - any other provider: `DuplicateAccount`.
  5. Cache the grant's access token; return the account.

**`TokenService<O, R, S, B, C>::access_token(account) -> Result<SecretString, EngineError>`**
(async)

1. A cached token that is valid for at least 60 more seconds is returned as is.
2. Otherwise read the refresh token (`Blocking::run`). None stored: `SignInRequired`.
3. `refresh` (async). `Rejected`: `SignInRequired`. `Network`: `Network`.
4. If the grant has a new refresh token, write it under the lock, only if the account still exists
   (note P1: a refresh racing a removal never leaves a token behind).
5. Cache and return the access token.

Two refreshes of one account at once both reach Google and both get valid tokens; deduplicating
them needs an async lock the engine does not have. Accepted for now: refreshes happen about once an
hour per account.

**`EngineError`** gains `SignInDenied`, `SignInFailed(source)`, `SignInRequired` and
`Network(source)`. Messages carry no address or token.

### New crate `clientmail-oauth`

Implements `OAuthClient` for Google. Holds protocol details only.

| Module | Role |
| --- | --- |
| `google.rs` | `GoogleOAuth::new(client_id)`. Redirect URI: the reversed client id as scheme, path `/oauth2redirect` (`com.googleusercontent.apps.<id>:/oauth2redirect`). Endpoints `accounts.google.com/o/oauth2/v2/auth` and `oauth2.googleapis.com/token`. Scopes `https://mail.google.com/ openid email profile` |
| `pkce.rs` | 32 random bytes as base64url for the verifier and for the state; `S256` challenge with `sha2` |
| `callback.rs` | Parses `code`, `state` or `error` out of the callback URL |
| `token.rs` | Form bodies for `authorization_code` and `refresh_token` grants (no client secret: Google's iOS-type clients have none), and parsing of the token response and of `{"error": ...}` bodies |
| `id_token.rs` | Decodes the ID token's payload (base64url JSON) and checks `iss`, `aud` (our client id), `exp` and `email_verified`. The signature is not checked: the token comes straight from Google's token endpoint over TLS, which OpenID Connect Core 3.1.3.7 allows |
| `http.rs` | One `reqwest::Client` (rustls, macOS trust settings through the platform verifier, the macOS HTTP and HTTPS proxy, 30 s timeout). Maps connect, timeout and TLS failures to `Network` |

### Decision record 0010: HTTP and TLS in Rust

| | A. `reqwest` + rustls with the platform verifier (recommended) | B. Swift `URLSession` behind a callback interface | C. `hyper` + `tokio-rustls` by hand |
| --- | --- | --- | --- |
| Size | Large dependency tree (hyper, rustls, a crypto provider) | Tiny on the Rust side | Same tree minus reqwest, plus our own glue |
| TLS for IMAP (1.6) | Same rustls stack and trust settings | IMAP still needs rustls, so two TLS stacks | Same as A |
| System trust, proxies | Trust: yes, through the platform verifier. Proxies: the HTTP and HTTPS proxy, read once (no PAC); see 0010 | Both, for free | Trust like A; no proxies |
| Rules | Network stays in Rust | Network for HTTP providers (Graph in 6.5) goes through Swift | Network stays in Rust |

Recommendation: A, because IMAP needs rustls anyway and one TLS stack is easier to reason about.
`core/AGENTS.md` asks before a large dependency, so this needs your approval. Exact crate features
(crypto provider, platform verifier) are pinned at implementation and recorded in the review log.

### FFI (`clientmail-ffi`)

- `CoreRuntime::spawn(future) -> impl Future<Output = T> + Send + 'static`: runs a future on the
  workers, resumes its panic in the caller. `RuntimeBlocking` (holds a `Handle` clone) implements
  `Blocking`, so spawned tasks reach the blocking pool without the client (note 1.5 P3).
  `SystemClock` implements `Clock`.
- `CoreClient::open(database_path, secrets, google_client_id: Option<String>)`, and the same for
  `open_in_memory`. `None` (no client id configured) disables Google sign-in.
- `CoreClient::google_sign_in_available() -> bool`.
- `CoreClient::begin_google_sign_in() -> Result<Arc<GoogleSignInSession>, CoreError>`.
- `GoogleSignInSession` (UniFFI object, used once):
  - `authorization_url() -> String`, `callback_scheme() -> String`;
  - `async complete(callback_url: String) -> Result<AccountRecord, CoreError>`: spawns the engine's
    `complete` on the workers and keeps its `AbortHandle`; a second call returns `SignInFailed`;
  - `cancel()`: aborts the task; `complete` then returns `SignInCancelled`.
- `CoreError` gains `SignInUnavailable`, `SignInCancelled`, `SignInDenied`, `SignInFailed`,
  `SignInRequired` and `Network`.

**Cancellation.** An abort stops the task at its next `.await`. Before the code exchange returns,
nothing is stored. The store-and-Keychain part is one blocking closure, which runs to the end even
if the task awaiting it is aborted. So a cancel that lands after the exchange can still add the
account, and the list shows it on its next load. This is the honest limit of cancelling a sign-in
that has already succeeded at Google.

### Swift

**Keychain (note P3).** `KeychainSecretStore.read` adds `kSecUseAuthenticationContext` with an
`LAContext` whose `interactionNotAllowed` is true, so a read never shows a prompt; a locked keychain
should then return `errSecInteractionNotAllowed`, already mapped to `Unavailable`. Writes and
deletes keep the default: they only happen while the user is signing in or removing an account. The
fake `KeychainClient` records the context; Acceptance 4 checks the real behaviour.

## Acceptance

You need the Google Cloud setup from `docs/google-oauth.md` first.

1. `make check` passes, with and without `Config/GoogleOAuth.xcconfig`.
2. Sign in with your Gmail account: the account appears with the Gmail provider and your Google name.
   Keychain Access shows one ClientMail item named `<account id>:oauth-refresh-token`.
3. Sign in again with the same account: still one account, still one item. Close the browser
   halfway through a third attempt: nothing changes and no error shows. Remove the account: the item
   is gone.
4. Locked keychain (note P3): with the app's account present, lock the login keychain
   (`security lock-keychain`), run `make keychain-test` (extended with a read of a locked item), and
   check that no prompt appears and the read reports unavailable.

## Risks and open questions

1. **Decisions to approve:** 0009 option A (a `Blocking` port), 0010 option A (`reqwest` with
   rustls, a large dependency).
2. **Google client type.** The plan uses an iOS-type OAuth client: no client secret, the reversed
   client id as redirect scheme, which `ASWebAuthenticationSession` can catch. Google documents that
   type for iOS; the Google Sign-In SDK uses it on macOS too, but I could not confirm it in Google's
   docs for Mac apps. If the console refuses it, the fallback is a "Desktop" client, which needs a
   loopback redirect (a local listener and the `network.server` entitlement) and ships a client
   secret that is not really secret. Checked in the first task, before any code depends on it.
3. **Split: new step 1.12.** Notes 1.3 P2 (pending deletions when the Keychain keeps failing) and
   the sweep half of P6 (orphaned Keychain items) need a migration, a store table, a new bridge call
   to list items, and a startup task. They do not affect signing in, so the plan moves them to a
   new step "1.12 Secret clean-up: pending deletions and orphaned Keychain items", depending on 1.4.
   Approve, or keep them here and make 1.4 larger.
4. **Testing mode.** While the OAuth app is in Testing, Google expires refresh tokens after 7 days
   and allows 100 test users. Expect `SignInRequired` weekly during development; signing in again
   fixes it (Acceptance 3). Publishing needs Google's verification of the restricted
   `mail.google.com` scope, a release concern.
5. **No ID token signature check.** Allowed for a token received directly from the token endpoint
   over TLS; the claims checks stay. Revisit if the ID token ever arrives another way.
6. **Client id in the repository.** The plan keeps it out (gitignored xcconfig). It is not a
   secret (every shipped app contains it), so committing it is also defensible and makes builds of
   a fresh clone sign-in ready. Keep it out, or commit it.
7. **Step size.** Even without the moved notes this is a full vertical slice (domain to UI). If you
   prefer smaller commits, it splits cleanly after task 5: core with fakes first, Swift and the real
   sign-in second.

## Review log

### Deviations found during implementation

1. **`OAuthClient::authorization` returns a `Result`.** It reads the OS random source, which can
   fail; the engine maps that to `SignInFailed`.
2. **`AccountStores`.** The repository, secret store, per-account locks and token cache live in one
   public `AccountStores<R, S>` that every account use case shares through an `Arc`.
   `AccountService::new` takes it instead of the two stores.
3. **Refresh results are saved under the lock, cache included.** `TokenService` writes a rotated
   refresh token and caches the access token in one blocking closure, only if the account still
   exists; otherwise it returns `AccountNotFound`.
4. **No system `Clock` in the FFI yet.** `TokenService` is not wired until 1.6, so a clock adapter
   would be dead code. Noted for 1.6.
5. **`SignInFlow` in the FFI.** `OAuthClient` cannot be a trait object (its methods return
   `impl Future`), so the client and the session hold the sign-in use case behind a small
   object-safe trait. The sign-in session tests are unit tests in `sign_in.rs`, because the
   constructor taking a fake OAuth client is crate-private; `tests/accounts.rs` covers
   availability through the public API.
6. **Sessions keep the runtime alive.** `CoreClient` holds its runtime in an `Arc`, shared with each
   `GoogleSignInSession`, so a session still completes if the client is dropped first.
7. **An invalid client id disables sign-in** instead of failing `open`, so a typo in the xcconfig
   never stops the app from launching.
8. **reqwest 0.13 features.** `rustls` (aws-lc-rs and the platform verifier), `form` and
   `system-proxy`: HTTPS honours the macOS proxy settings after all. Decision record 0010 says so.
   The static library then needs `SystemConfiguration` and `Security`, linked from the `CoreBridge`
   target in `Package.swift`.
9. **Swift names.** The protocol is `SignInSession`, not `GoogleSignInSession`, which would clash
   with the generated type inside `CoreAdapter`. `isGoogleSignInAvailable()` and
   `beginGoogleSignIn()` are `async` functions, so actor fakes can implement them.
10. **`CoreError.SignInRequired` maps to `signInFailed` in Swift** until 1.6, the first call that
