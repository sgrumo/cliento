# 1.6: IMAP crate: TLS connect, XOAUTH2, list folders

Status: done

The design below is the approved plan. The adversarial review reopened decision record 0011: the
crate now uses `imap-next` and `imap-codec` instead of `async-imap`, and the review changed the
domain types and the session's rules. The Review log lists each change; the code follows the log
where the two differ.

## Goal

The core can open a TLS connection to an IMAP server, sign in with XOAUTH2 using a Google access
token, and list the account's folders with their roles (Inbox, Sent, All Mail, ...). The protocol
is tested against scripted server transcripts, and once against your real Gmail account. The sync
engine (1.8) builds on this; nothing is visible in the app yet.

## Design

### Decision record 0011: the IMAP library

| | A. `async-imap` 0.12 (recommended) | B. `imap-next` + `imap-codec` 2.0 | C. Our own client on `imap-proto` |
| --- | --- | --- | --- |
| Maturity | Used in production by Delta Chat; parser `imap-proto` 0.17 | Thorough, misuse-resistant types, but 2.0 is still alpha (API churn) | The parser is mature; the client is ours to write |
| Fits us | Tokio feature, generic over any stream, `AUTHENTICATE` with a custom authenticator, `LIST` with special-use attributes, Gmail fetch items (`X-GM-LABELS`, `X-GM-MSGID`, `X-GM-THRID`), `IDLE` | Sans-I/O: we write the connection loop; every extension available | Everything we need, at the cost of tags, literals, continuations and response routing |
| Code to own | Small adapter | Medium | Large |
| Risk | Its `log::trace!` prints raw protocol lines, tokens included, if a logger is ever installed | Alpha releases | Bugs in our own protocol handling |

Recommendation: A. It covers 1.6, 1.7 and 2.7 (IDLE) with a small adapter, and Delta Chat
exercises it against many servers. The logging risk is contained: the app installs no logger, and
the rule for any future one is to cap `async_imap` at `warn` (recorded in 0011 and
`core/AGENTS.md`). If it ever blocks us, the adapter is the only code that changes, because the
engine sees only the domain port.

### Domain (`clientmail-domain`)

New module `imap.rs`, and the ports in `ports.rs`:

```rust
/// Where an IMAP server listens. Implicit TLS only, for now.
pub struct ImapServer { host: String, port: u16 }
impl ImapServer { pub fn gmail() -> Self; /* imap.gmail.com:993 */ }

/// A folder as the server lists it, before it has a local id.
pub struct RemoteMailbox { path: MailboxPath, role: MailboxRole, selectable: bool }

/// A server's folders, and how many it listed that could not be used (invalid names).
pub struct MailboxListing { mailboxes: Vec<RemoteMailbox>, skipped: usize }

pub enum MailErrorKind {
    AuthenticationFailed, // the server refused the token: refresh it, or sign in again
    Network,              // no connection, TLS failure, timeout, connection dropped
    Protocol,             // the server said something we cannot use
}

pub trait MailConnector: Send + Sync + 'static {
    type Error: Error + Send + Sync + 'static;
    type Session: MailSession<Error = Self::Error>;
    fn error_kind(error: &Self::Error) -> MailErrorKind;
    /// Connects, checks the server offers XOAUTH2, and signs in.
    fn connect(&self, server: &ImapServer, user: &EmailAddress, access_token: &SecretString)
        -> impl Future<Output = Result<Self::Session, Self::Error>> + Send;
}

pub trait MailSession: Send {
    type Error: Error + Send + Sync + 'static;
    fn list_mailboxes(&mut self) -> impl Future<Output = Result<MailboxListing, Self::Error>> + Send;
    fn logout(self) -> impl Future<Output = Result<(), Self::Error>> + Send;
}
```

- `ImapServer::gmail()` lives in the domain because which server a provider uses is account
  configuration, not protocol; 6.1 adds discovery next to it.
- `RemoteMailbox` and `MailboxListing` redact folder names in `Debug`, like `MailboxPath`.
- The port speaks IMAP's vocabulary (folders, sessions); Microsoft Graph (6.5) gets its own port.

### New crate `clientmail-imap`

| Module | Role |
| --- | --- |
| `tls.rs` | TCP connect and TLS with `tokio-rustls`, the aws-lc-rs provider and `rustls-platform-verifier` (the same stack and trust settings as HTTPS, decision record 0010). 30 s connect timeout |
| `xoauth2.rs` | The SASL string `user=<address>\x01auth=Bearer <token>\x01\x01`, base64 by `async-imap`. On failure Gmail sends a base64 JSON challenge; the authenticator answers it with an empty response, as RFC 7628 requires, and the server then says `NO` |
| `session.rs` | `ImapSession` over any stream (`AsyncRead + AsyncWrite`), so tests drive it with an in-memory pipe. Reads the greeting, checks `AUTH=XOAUTH2` in the capabilities (asking with `CAPABILITY` if the greeting has none), authenticates, `LIST "" "*"`, `LOGOUT`. Every command has a 60 s timeout |
| `roles.rs` | Folder attributes to `MailboxRole`: `INBOX` by name; `\All`, `\Archive`, `\Drafts`, `\Sent`, `\Trash`, `\Junk`, `\Flagged` (Starred), Gmail's `\Important`; anything else is `Custom`. `\Noselect` and `\NonExistent` make a folder not selectable |
| `utf7.rs` | Decodes modified UTF-7 folder names (RFC 3501, 5.1.3): `&`-shifted UTF-16BE in base64 with `,` for `/`. A name that does not decode, or that `MailboxPath::new` rejects, is skipped and counted (note 1.1 C6) |
| `error.rs` | `ImapError` with `Network`, `AuthenticationFailed`, `NoXoauth2`, `Protocol(&'static str)`. Messages never include the token, the address or folder names |
| `lib.rs` | `ImapConnector` implementing `MailConnector` |

Classification: an `AUTHENTICATE` answered with `NO` is `AuthenticationFailed` (1.8 refreshes the
token once and retries, then asks the user to sign in again); I/O errors, TLS errors and timeouts
are `Network`; everything else is `Protocol`.

### Transcript tests

A transcript is a text file of the conversation, one line per exchange:

```
S: * OK [CAPABILITY IMAP4rev1 ... AUTH=XOAUTH2 ...] Gimap ready
C: A0001 AUTHENTICATE XOAUTH2 {xoauth2}
S: A0001 OK ada@gmail.com authenticated (Success)
C: A0002 LIST "" "*"
S: * LIST (\HasNoChildren) "/" "INBOX"
...
```

- A scripted server (`tests/support/script.rs`) plays the `S:` lines on one end of a
  `tokio::io::duplex` pipe, and checks each line the client sends against the next `C:` line.
  `{xoauth2}` stands for the expected SASL string, computed from the test's address and token.
- Transcripts in `tests/transcripts/`: Gmail sign-in and folder list; Gmail refusing the token
  (JSON challenge, then `NO`); a server without `XOAUTH2`; a list with special-use attributes, a
  `\Noselect` parent, modified UTF-7 names and one invalid name; a connection dropped mid-list.
- They are written by hand from RFC 3501, RFC 6154, RFC 7628 and Google's XOAUTH2 documentation,
  not recorded: a recording of a real account holds its folder names and address. Each file says
  where its lines come from.

### Opt-in test against Gmail

`make imap-smoke` runs one ignored test with `CLIENTMAIL_IMAP_USER` and `CLIENTMAIL_IMAP_TOKEN`
set: it connects to `imap.gmail.com`, lists the folders and checks that `INBOX` is the Inbox and
that All Mail, Sent, Drafts and Trash have their roles. It prints only counts per role, never
names. The token comes from Google's OAuth 2.0 Playground (`docs/google-oauth.md` gets a short
section), because the app cannot hand one out before 1.8.

## Risks and open questions

1. **Decisions to approve:** the scope (A, crate and port only, five notes moved to 1.8) and
   decision record 0011 (A, `async-imap`). `core/AGENTS.md` asks before a large dependency;
   `async-imap` with its parser is one.
2. **Logging inside `async-imap`.** It traces raw protocol lines through `log`, which would include
   the XOAUTH2 token. Nothing installs a logger today. The rule added to `core/AGENTS.md` keeps it
   that way unless the logger caps `async_imap` at `warn`; a test cannot enforce this.
3. **Hand-written transcripts** can disagree with what Gmail really sends. The opt-in Gmail test is
   the check; differences it finds become transcript fixes.
4. **The Playground token** belongs to Google's Playground client, not ours. That is fine for an
   IMAP test: Gmail checks the token's scope, not which client asked for it.
5. **Gmail's XOAUTH2 failure flow** (a JSON challenge before `NO`) must be answered or the
   connection hangs. The transcript test covers it; the timeout bounds it if Gmail changes.

## Review log

### Deviations found during implementation (first version, on `async-imap`)

These applied to the `async-imap` version and led to the review's finding P1; most of the code they
describe was replaced (see "Library switch" below).

1. `async-imap`'s `list` stream ended quietly at end of file and treated a tagged `NO` as
   completion; the session sent `LIST` itself and accepted only the tagged `OK`.
2. Gmail's greeting has no capability list, and `async-imap` could not send tagged commands
   before signing in, so the session wrote `C0 CAPABILITY` to the stream itself.
3. `async-imap` sent the XOAUTH2 string after the server's `+` (no SASL-IR).
4. `async-imap` does not export its raw response type; responses were inspected in a closure.
5. `futures-util` was dropped. Non-ASCII names were kept as UTF-8; multi-character delimiters
   skipped. The rustls provider is named explicitly. The crate is not linked into the app before
   1.8, so the app's size does not change.

### Library switch (review P1)

The review found that `async-imap`'s `SELECT`, `FETCH` and `IDLE` have the same flaw as its `list`,
and that its parser (`imap-proto`) keeps escapes in quoted strings and matches `\All`/`\Sent` as
prefixes. With your decision, the step spiked `imap-next` 0.3 + `imap-codec` 2.0 against the same
transcripts (scratch space, not committed). Results, recorded in decision record 0011:

- Both libraries passed the seven transcripts; `async-imap` only after replacing its `list`.
- A probe listing (escaped quote and backslash, a `\` delimiter, a literal name, `\AllMail`,
  `\Sentinel`, a non-UTF-8 literal) failed as a whole on `async-imap` (reported as a network
  error) and was parsed correctly on `imap-next`, the non-UTF-8 name skipped and counted.
- `imap-codec` has no Gmail `X-GM-*` fetch items; 1.7 must add them (note in the step index).
- `imap-codec` 2.0.0-alpha.9 needs `nom`'s `alloc` feature added by hand.

`imap-next` won. The crate now:

- drives `imap-next`'s sans-I/O client over any stream with its own small read/write loop, keeping
  our TLS and the in-memory test pipe;
- sends every command with its own tags (`A0001`, ...) and reads until that tag; uses SASL-IR when
  the server offers it, as Gmail does, and otherwise answers the first `+`;
- skips and counts a `LIST` line `imap-codec` cannot parse instead of failing the listing.

Transcripts changed only in tags and SASL-IR; their content is the same.

### Deslop

Six edits by the deslop agent, one follow-up by me, no behaviour change, `make check` green:

- `tls.rs`: one `let mut config` instead of a rebinding.
- `session.rs`: `capabilities.contains(...)` instead of a one-line closure.
- `utf7.rs`: `char::decode_utf16` instead of a temporary `Vec<u16>` (one allocation less;
  unpaired surrogates still rejected).
- `clientmail-imap/Cargo.toml`: the redundant `base64` dev-dependency removed.
- `core/Cargo.toml`: the unused `clientmail-imap` entry in `[workspace.dependencies]` removed; 1.8
  adds it back when the FFI uses the crate. The crate stays a workspace member.
- `tests/transcripts.rs`: one `folders()` helper for two identical mappings.
- Follow-up: `a_server_without_sasl_ir_gets_the_credentials_after_its_continuation` now also checks
  that `open` succeeded (deslop may not change coverage).

Left alone on purpose: `to_string()` on each folder attribute in `roles.rs` (matching variants
directly could change which spellings match), the bounds-checked buffer slice in `session.rs`
(the lints forbid indexing), and the plan's original Design text (the header note says the Review
log wins).
